Date: 2026-08-12 Status: Superseded

This spec documents a two-pass design that was implemented, failed its manual gate repeatedly, and was reverted in favour of idleTimeout: 0. The Problem and Goal remain valid; the Design is kept as a record of what was tried and why it was abandoned.

Problem

idleTimeout currently decides "active" purely from a .jsonl file's mtime at the file-listing step — older files are never even read. This was acceptable before open-tab detection landed, but now the extension knows when a tab is genuinely still open via vscode.window.tabGroups, yet lets it vanish from the bar just because the user hasn't sent a new message in a while. A tab you're still looking at disappearing reads as broken.

Goal

A tab confirmed open via vscode.window.tabGroups must never disappear from the status bar purely from elapsed time. Only idleTimeout-driven disappearance for tabs that are not confirmed open is unaffected.

Non-goals

  • Cross-window / onlyCurrentWindow: false. Same restriction as the closed-tab fix — tabGroups only sees this window's tabs, so resurrection past idleTimeout only applies when onlyCurrentWindow is true.
  • A user-facing setting for the extra-scan bound. The 20-file-per-project safety cap is an implementation detail, not a behaviour knob — no new claudeContextBar.* setting.
  • Unbounded history scans. One project directory holds 930 .jsonl files; nothing here may read at a cost that scales with that number in the common case.

Design (Attempted)

The insight: search is demand-driven, not size-driven

An initial approach considered flatly reading "the N most recent files per project regardless of idleTimeout" — but N is either too small (misses a tab idle longer than N other sessions' worth of activity) or too costly at scale. The fix: don't guess a file count — know exactly which open tabs need resolving, and stop reading the moment they're found.

Pass 1 (unchanged)

For each project directory, list .jsonl files with mtime > cutoffTime (today's idleTimeout cutoff), read them, and build SessionInfo[]. Every tab still being actively used lands here — this is the common case, and nothing about its cost changes.

Between passes

Only when onlyCurrentWindow is true:

  1. openTabTitles = getOpenClaudeTabTitles() (unchanged).
  2. reliable = detectionLooksReliable(sessions, openTabTitles) (unchanged).
  3. If reliable: find unmatchedTitles — open tab titles that don't correspond to any Pass 1 session. An empty list (the overwhelmingly common case) means Pass 2 never runs at all.

Pass 2 (new, conditional)

Only runs when unmatchedTitles is non-empty. For each project directory, in mtime-descending order, read .jsonl files older than cutoffTime one at a time — stopping as soon as unmatchedTitles is empty, or after 20 files for that project (MAX_EXTRA_SCAN_PER_PROJECT), whichever comes first. A file whose lastPrompt matches one of unmatchedTitles becomes a session, unconditionally kept, and its title is removed from unmatchedTitles.

New primitive: matchingOpenTabTitle

A new function in src/openTabMatch.ts performs the same prefix-match rule as hasMatchingOpenTab, but returns which title matched (or undefined) instead of a boolean. Crucially, it has no vacuous pass for an empty prompt — Pass 2 hunts for a positive, named correlation to a specific open tab; an old session with no recorded prompt proves nothing.

Final assembly

liveSessions = reliable
    ? pass1Sessions.filter(s => hasMatchingOpenTab(s.lastPrompt, openTabTitles))
    : pass1Sessions;
liveSessions = [...liveSessions, ...pass2Sessions];

pass2Sessions need no re-filtering: each one only exists because it already matched a specific unmatched title.

Testing (as specified)

src/openTabMatch.test.ts cases for matchingOpenTabTitle:

Case Expected
Prompt's ellipsis-truncated prefix matches a title in the list Returns that title
No title matches undefined
Empty prompt, non-empty title list undefined (no vacuous pass here)
Two titles, prompt matches the second one Returns the second title, not the first

hasMatchingOpenTab's existing 8 cases must still pass unchanged after the refactor (regression check).

Manual gate (required): in the Extension Development Host, temporarily set claudeContextBar.idleTimeout to something small (e.g. 10) in workspace settings, open a tab, send a message, then leave it untouched past 10s. Confirm the item stays visible (Pass 2 resurrecting it). Then close the tab and confirm it still disappears promptly (regression check). Restore idleTimeout afterward.

Risks

  • Pass 2 only runs when there's at least one unmatched open tab — zero extra file reads in the common case. Worst case reads up to 20 extra files per project per refresh cycle, not the full history.
  • A tab idle long enough that more than 20 other sessions in the same project were touched afterward still falls back to disappearing at idleTimeout — same accepted trade-off as the flat-cap design, just at a higher and demand-scoped bound.
  • Still bound by onlyCurrentWindow: true and detectionLooksReliable — unreliable detection skips special handling and falls back to plain idleTimeout.

Amendment: Why Pass 2 was reverted

Pass 2 was implemented and failed its manual gate three times, each failure landing in a different place. Under the systematic-debugging rule that 3+ failed fixes indicate a wrong architecture rather than three unlucky bugs, it was reverted.

Root cause: the matching key is not unique. Sessions are correlated to tabs by title text, and a tab's title is derived from the session's last prompt. Verified on disk: six sessions, with "teste" appearing as the last prompt of two different session files and "oi" of two others. A non-unique key cannot reliably answer "which session is this tab?", and each fix — a detectionLooksReliable rewrite, a supersession gate, then a bounded older-file scan — moved the failure somewhere else rather than removing it.

The true identity (unreachable at runtime)

The webview's serialized state carries {"sessionID":""}. This is the unique identifier that would solve the problem — but it is not reachable at runtime. vscode.window.tabGroups exposes only viewType and label on TabInputWebview, and the Claude Code extension's sessionPanels map (keyed by session id) is a private field. Verified by reading both the API surface and the extension bundle. Title text is the only runtime signal available, and no amount of extra machinery makes a non-unique key unique.

What replaces Pass 2: idleTimeout: 0

claudeContextBar.idleTimeout: 0 — an already-supported value meaning "never hide by time" — makes cutoffTime zero, so every session file in the project enters the normal Pass 1 scan and the already-verified open-tab filter is the only thing deciding what shows. That achieves this spec's Goal with no new mechanism:

  • Tab open → its session is read (no cutoff to fall out of) → matches → shown.
  • Tab closed → dropped by the closed-tab filter, exactly as before.

Cost of idleTimeout: 0: every session file in the workspace's project directory is parsed on each refresh instead of only recently-modified ones. Acceptable for normal projects; one directory on this machine holds 930 .jsonl files, so if that workspace is opened directly, an mtime-keyed parse cache is the follow-up — deliberately not built yet, since no measurement shows it is needed.

What was kept from Pass 2 work

Two pieces of the Pass 2 implementation were retained because they are correct independent of it:

  • matchingOpenTabTitle (openTabMatch.ts), now backing hasMatchingOpenTab. This primitive is sound and improves the matching logic.
  • The openTabsVerified gate on the supersession heuristic. Supersession infers "abandoned" from creation-time ordering alone, which is wrong for several genuinely open tabs of one project — an older tab merely gone quiet is indistinguishable from an abandoned one by that rule. When open tabs are positively verified, that guess must not override the verified result. Confirmed live: without this, only the focused tab survived.
